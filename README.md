# Grimoire — Compact Dual Dynamic LLM

[![Model on HF](https://img.shields.io/badge/Hugging%20Face-Model-yellow)](https://huggingface.co/embrelgrim/grimoire)
[![License: Apache 2.0](https://img.shields.io/badge/License-Apache_2.0-blue.svg)](LICENSE)

Экспериментальная компактная русскоязычная языковая модель с рекуррентной
фабрикой весов и протоколом вызова `calculate` / `web_search`.
Основная реализация архитектуры, обучения и чата находится в одном файле
`build_neuroset.py`; скрипты оценки вынесены отдельно.

**Статус:** исследовательский прототип, не надёжный универсальный ассистент.
Модель умеет формировать вызовы инструментов, но может выбирать неверный запрос,
искажать результат поиска и отвечать не по задаче. Наличие источника в контексте
не гарантирует достоверности финального ответа.

> **Исправление методики оценки.** Ранее опубликованные BPB собственной модели
> и оценки `8/8`, `76/91`, `77/91` не подтверждают качество, заявленное в прежнем
> README. BPB вычислялся с утечкой будущего через фабрику и lossy-маппингом токенов;
> проверка ответа искала факт во всей трассе, включая ответ инструмента.
> `bench_results.json` сохранён как архив с предупреждениями, не как актуальный
> рейтинг. Результаты повторного запуска приведены ниже; они не восстанавливают прежние
> заявления о семантической точности или превосходстве модели.

## Модель

| Свойство | Значение |
|---|---|
| Основной чекпойнт | [`embrelgrim/grimoire`](https://huggingface.co/embrelgrim/grimoire), локально `runs/assistant8` |
| Параметры | 35 849 352 |
| Размерность | `d_model=896`, 14 голов × 64 |
| Базовый блок | Слой с индексом 6 из `Qwen/Qwen2.5-0.5B-Instruct`, GQA с 2 KV-головами |
| Рекуррентная глубина | 8 шагов с переиспользованием базового слоя |
| Compact-словарь | 11 264 токена, tied embeddings / LM head |
| Заявленный целевой train-набор | 65 490 сэмплов / 40 030 505 токенов |
| Заявленное время целевого обучения | Около 8 часов на RX 6600 8 ГБ; не включает предобучение Qwen |
| Больший экспериментальный вариант | `assistant_big6`, около 129M параметров |

Размер данных и время приведены по описанию исходного эксперимента, а не по
новому воспроизведению. Используются предобученные компоненты Qwen: это не
обучение всей модели с нуля за восемь часов. Указанное ранее покрытие 99.84%
относится к корпусу построения словаря, а не ко всем возможным входам.

## Быстрый старт

Установите PyTorch под своё устройство, затем зависимости. Для AMD нужна
совместимая сборка PyTorch/ROCm; обычная установка `torch` не гарантирует
поддержку конкретной карты. Скрипт использует `HSA_OVERRIDE_GFX_VERSION`, но это
не заменяет совместимость драйвера и ROCm.

```bash
pip install transformers numpy huggingface_hub
hf download embrelgrim/grimoire \
  --local-dir runs/assistant8 \
  --include "checkpoints/*.pt" "compact_vocab.pt" "config.json" "tokenizer/*"

python build_neuroset.py --mode chat --run runs/assistant8
python build_neuroset.py --mode chat --run runs/assistant8 \
  --prompt "сколько будет 47 * 13?"
python build_neuroset.py --mode bench --run runs/assistant8
```

Команды выполняются из корня репозитория. Совместимость конкретного сочетания
версий `torch` и `transformers` требует проверки; зафиксированное проверенное
окружение пока не опубликовано. Для воспроизведения сохраняйте `pip freeze`,
версию ROCm, GPU, commit кода и ревизию/хеш чекпойнта.

Загружайте `.pt` только из доверенного источника: текущие загрузчики используют
`torch.load(..., weights_only=False)` и могут десериализовать Python-объекты.

## Архитектура

1. Compact token embedding складывается с `0.1 × byte-morph patcher`
   (представление первых 8 байт токена).
2. Фабрика получает контекст, состояние GRU по глубине и embedding номера шага.
   Она порождает per-head веса attention и MLP.
3. На каждом шаге выполняются переиспользуемый базовый слой Qwen и
   сгенерированный блок, затем gated residual update.
4. Итоговые hidden states проходят через RMSNorm и tied LM head.

`W_o` и `W_out` сгенерированного блока инициализируются нулём. Это относится
к сгенерированной ветви, а не означает, что весь рекуррентный шаг тождественен.

Дополнительные шаги дают больше вычислений, но сами по себе не доказывают
улучшение рассуждения. Основные веса общие. При `d_model=896` каждый
дополнительный шаг добавляет 897 параметров: embedding глубины и scalar gate.
Вычислительная стоимость и объём кэша при увеличении глубины растут.

### Каузальность и кэш

При обучении ответов и генерации фабрика использует якорь `anchor_lens`, чтобы
не читать будущую часть ответа. После ответа инструмента начинается новый
сегмент с обновлённым якорем. Прямой вызов `model(x)` без якоря не является
корректным способом оценить авторегрессионную вероятность всех позиций `x`:
фабрика может читать будущие токены.

Есть `prefill_cached` / `step_cached`. Утверждение о побитовом совпадении с полным
пересчётом требует отдельного теста для конкретного окружения. В частности,
режим `factory_prefix>0` требует проверки: cached и обычный forward обрабатывают
ограничение префикса по-разному. Кэш и архитектура в этой ревизии не изменялись.

### Ограничение compact-словаря

Исключённый исходный токен отображается в сохранённый префикс либо ID 0, а не
в обратимую последовательность байтов. Поэтому возможна потеря частей текста,
особенно на редких словах и вне обучающего распределения. Byte-morph patcher
не восстанавливает информацию, уже потерянную при маппинге.

Существующий чекпойнт сохранён совместимым. Замена словаря на обратимое
кодирование — отдельная задача, потенциально требующая переобучения.

## Данные и обучение

Скрипт сам не собирает готовый датасет. Укажите папку с `train.jsonl` и
`val.jsonl` либо явные `--train-file` / `--val-file`.

```bash
# Пример запуска, не полный рецепт воспроизведения опубликованного чекпойнта
python build_neuroset.py --preset qwen36m --data-dir YOUR_DATA_DIR \
  --out runs/base --hours 5 --max-seq-len 768 \
  --lr 2e-4 --lr-base 4e-5 --warmup 400 --yes

# Продолжение с сохранённым словарём
python build_neuroset.py --preset qwen36m --data-dir YOUR_NEXT_DATA_DIR \
  --out runs/next --init-ckpt runs/base/checkpoints/best.pt \
  --vocab-pack runs/base/compact_vocab.pt \
  --hours 1 --max-seq-len 768 --lr 4e-5 --lr-base 1e-5 --warmup 200 --yes
```

Пресеты: `qwen36m`, `night-scratch`, `night-scratch-pro`, `smoke`.
В исходном описании приведён val loss около 2.55. Это внутренняя метрика
конкретного train/val-протокола, не сопоставимый между моделями BPB.

## Чат и инструменты

По умолчанию история между сообщениями не переносится: модель не обучена
надёжному многоходовому диалогу. Экспериментальная склейка истории:

```bash
python build_neuroset.py --mode chat --run runs/assistant8 --chat-context
```

- `calculate`: разбор арифметического выражения без Python `eval`.
  Верный результат калькулятора не гарантирует, что модель составила правильное
  выражение или правильно передала результат пользователю.
- `web_search`: локальная база Википедии при её наличии, затем сетевые fallback.
  Описанная ранее локальная база `kb/` не входит в этот репозиторий; без неё
  поведение и ответы могут отличаться от исходного эксперимента.

Модель генерирует tool-call JSON; рантайм исполняет поддерживаемые вызовы.
Финальный синтез остаётся ненадёжным. Например, в архивном результате на вопрос
о столице Франции инструмент вернул Париж, но финальный текст модели говорил
про Францию «расположенную в Германии». Это ошибка, а не успешный grounded-ответ.

## Оценка: что исправлено и что ещё не доказано

### Архивные результаты

`bench_results.json` содержит исходные числа и тексты, помеченные
`legacy_invalid_for_quality_comparison`. Не используйте их как рейтинг:

- BPB собственных моделей имел утечку будущего через factory context/frontier;
- lossy-маппинг оценивал изменённые токены, а знаменатель содержал байты оригинала;
- instruction/tool scores учитывали факт внутри `<tool_response>`;
- скорость описывалась как fp16, хотя опубликованный загрузчик использует float32.

Повторные измерения представлены в следующем разделе. 

### Результаты повторного запуска

Ниже приведены результаты из консольного лога после
исправления оценивания. Это не независимое воспроизведение. GPU — AMD Radeon
RX 6600; собственный чекпойнт — `runs/assistant8/checkpoints/final.pt`.
Версии зависимостей и хеш весов в этом логе не зафиксированы.

**Выполнено:** 6 unit-тестов, `eval_det.py`, `eval_ood.py`,
`bench_suite.py instr` и `bench_suite.py speed`.
Все 6 unit-тестов прошли; они проверяют код оценивания, а не качество модели.

#### Фиксированные ответы инструментов — `eval_det.py`

| Проверка | Результат | Что именно проверяется |
|---|---:|---|
| WEB query | 27/39 | Допустимый текстовый маркер в запросе `web_search` |
| WEB answer | 22/39 | Маркер факта в финальном тексте, не во всей tool-трассе |
| CALC | 7/8 | Ожидаемый числовой токен в финальном ответе |
| CALIB | 5/5 | Нет вызова инструмента на пяти контрольных репликах; базовая проверка текста |
| Lexical overlap | 0.42 | Средняя доля учитываемых слов ответа, встречающихся в эталонном tool response |

В предыдущем описании WEB answer был 37/39; после устранения зачёта фактов
внутри ответа инструмента текущий прогон дал 22/39. Это изменение методики,
а не доказательство ухудшения весов. Арифметика прошла 7 из 8 примеров;
на `sqrt из 144` модель ошибочно выбрала поиск вместо калькулятора.

Даже новые `[OK]` не означают правильности всего ответа. Например:

- «Луна — ежегодное озеро на Земле: чемпионат мира по футболу» проходит по слову «Луна»;
- ответ про «Войну и мир» упоминает Толстого, но добавляет выдуманный 1930 год;
- запрос «Горубинская впадины» проходит query-проверку по общему слову «впадин».

Поэтому 22/39 нельзя публиковать как точность grounded-синтеза, а 27/39 — как
долю строго правильно извлечённых сущностей. Для таких метрик нужна более
строгая разметка и проверка утверждений.

#### Реальные инструменты — `eval_ood.py`

| Проверка | Результат | Интерпретация |
|---|---:|---|
| CALC | 7/8 | Совпадение ожидаемого числа в финальном ответе |
| WEB | 2/12 | Маркер в финальном ответе при наличии tool response |
| GEN | 8/8 | Только базовые проверки формата, длины и отсутствия обнаруженной деградации |
| CALIB | 5/5 | Отсутствие вызовов инструментов на контрольных репликах и базовые проверки текста |
| Сумма, напечатанная скриптом | 22/33 (67%) | Смесь разных эвристик, **не 67% корректных ответов** |

GEN=8/8 не подтверждает следование инструкциям: просьба придумать название
кофейни привела к поиску и просьбе уточнить запрос, а объяснение дружбы — к
нерелевантному тексту. WEB-прогон включает как ошибки модели, так и неудачи
поиска: для Байкала, Японии и ряда других запросов инструмент вернул «не нашёл».
Причину этих неудач по одному логу установить нельзя. Наборы WEB в двух
скриптах различаются, поэтому 22/39 и 2/12 нельзя напрямую сравнивать как
эффект замены oracle-контекста реальным поиском.

#### Что именно сравнивается

Цель прикладного сравнения — **качество ответа готового ассистента**, а не
только знания, хранящиеся в весах. Grimoire оценивается вместе со штатными
`calculate` и `web_search`: способность выбрать инструмент, сформировать вызов
и использовать результат — часть функциональности проекта и его преимущество.
Отключать инструменты ради выравнивания возможностей здесь не требуется.

Сравнение готовых систем допустимо, но не заменяет абляцию архитектуры при
одинаковом окружении. Успешный вызов калькулятора — достижение всей системы,
а не свидетельство того, что нейросеть сама выполнила умножение.

#### Содержательная оценка сохранённых ответов

После прогона отдельно просмотрены все 157 ответов из трёх JSON, включая
72 ответа девяти моделей в instruction-тесте. Это **оценка ИИ-ассистентом по
явной рубрике**, не независимая человеческая разметка и не новый запуск.

- **Зачёт:** задача выполнена связно, без существенных ошибок и разрушающего
  продолжения.
- **Частично:** есть правильная полезная часть, но ответ неполон, искажён либо
  содержит выдумки. В число полностью решённых задач не входит.
- **Незачёт:** основной ответ неверен, отсутствует или не относится к задаче.

Для WEB дополнительно оценивается опора на предоставленный источник.
Утверждение вне источника не обязательно ложно, но может лишить ответ строгого
зачёта за grounded-синтез. Пограничные оценки открытых задач субъективны;
внешний фактчекинг всех деталей не выполнялся. Оценивается весь финальный
ответ, а не только удачная первая фраза.

| Набор Grimoire | Зачёт | Частично | Незачёт |
|---|---:|---:|---:|
| `eval_det`: WEB, фиксированные tool responses | 3 | 10 | 26 |
| `eval_det`: CALC | 7 | 0 | 1 |
| `eval_det`: CALIB | 5 | 0 | 0 |
| `eval_ood`: WEB, реальные инструменты | 0 | 2 | 10 |
| `eval_ood`: CALC | 7 | 0 | 1 |
| `eval_ood`: GEN | 1 | 1 | 6 |
| `eval_ood`: CALIB | 5 | 0 | 0 |

В фиксированном WEB чистые зачёты получили ответы о Пушкине, Марсе и Python.
Все семь вопросов о столицах остались без названия столицы в финальном ответе,
хотя оно присутствовало в tool response. Это указывает на проблему выбора
нужного факта из контекста. Часто модель воспроизводит начало определения,
но не отвечает на запрошенный атрибут.

В реальном WEB два частичных ответа — Париж и Пушкин: правильная часть
сопровождается выдуманной географией или искажённой биографией. В шести трассах
инструмент вернул «не нашёл», причём в пяти запрос был по существу уместным.
Это отдельная проблема поиска/доступности; честный отказ в таком случае лучше
выдумки, но исходная задача всё равно не решена.

**Арифметика 7/8 и пять контрольных социальных реплик подтверждаются по смыслу.**
Слабые места текущего чекпойнта — извлечение целевого факта, сохранение точности
при пересказе и выполнение открытых инструкций.

### Текущие проверки

`eval_utils.py` отделяет финальный ответ от tool-трассы. Арифметика проверяется
по совпадению числового токена, а не произвольной подстроки. Это всё ещё эвристика:
она не доказывает смысловую корректность и может пропустить противоречивый ответ.

`bench_suite.py instr` — восемь smoke-test вопросов, а не полноценный тест
следования инструкциям. Автоматические баллы — наличие маркеров/проверка формата,
не доля осмысленно решённых задач. Содержательная оценка сохранённых текстов
приведена выше. Сравниваются готовые конфигурации ассистентов: Grimoire со своим
tool-рантаймом и конкуренты в режиме текстовой генерации. Поддержка инструментов
считается функциональным преимуществом системы, а не причиной исключать результат.
Этот тест не изолирует вклад архитектуры от инструментов и обучения.

`eval_det.py` подставляет эталонный ответ инструмента независимо от запроса:
это oracle-context тест. Он отдельно проверяет маркер в query и финальном ответе.
39 WEB-вопросов дают две проверки каждый; вместе с 8 CALC и 5 CALIB получается
91 проверка, **не 91 независимая задача**. `lexical_overlap` — пересечение слов,
не factual faithfulness. Даже корректное совпадение маркера не гарантирует
правильности всего предложения.

Сопоставимый BPB собственной модели **отключён**, а не «исправлен одной маской».
Для восстановления нужны каузальный протокол и обратимое кодирование текста.
BPB HF оставлен как диагностический legacy-протокол с неперекрывающимися окнами:
первые токены окон пропускаются, знаменатель включает весь текст. Для строгого
рейтинга нужен единый уточнённый протокол и учёт оцениваемых байтов.

Скорость измеряется опубликованными загрузчиками в float32. Токены разных токенизаторов не эквивалентны, поэтому tok/s
не является прямым сравнением скорости выдачи одинакового объёма текста.

### Команды

```bash
# После установки зависимостей и скачивания нужных собственных чекпойнтов:
python bench_suite.py instr --output bench_results_v2.json --force
python bench_suite.py speed --output bench_results_v2.json --force
python bench_suite.py hf --output bench_results_v2.json --force

# ours сообщает, что comparable BPB отключён; all запускает остальные секции тоже
python bench_suite.py ours

python eval_det.py --run runs/assistant8 --show --json-out eval_det_v2.json
python eval_ood.py --run runs/assistant8 --show --json-out eval_ood_v2.json
python -m unittest discover -s tests -v
```

Новые результаты пишутся в отдельный `bench_results_v2.json`. Без `--force`
прогон продолжает результаты схемы v2; меняя чекпойнт или окружение, используйте
новый output-файл. Скрипты сравнения также перечисляют `night_glm9q` и
`assistant_big6`: промежуточные и эксперементальные модели, возможно опубликованные позже.

## Масштабирование и ограничения выводов

Вариант около 129M использует базовый слой Qwen2.5-1.5B и более широкий словарь.
Его существование демонстрирует возможность построить более крупную модель,
но не доказывает улучшение качества или преимущество фабрики весов.
Нужны абляции с фиксированными весами, без фабрики, с разной глубиной и
сопоставимым бюджетом вычислений, а также независимый тестовый набор.

Основные ограничения: lossy-словарь, ненадёжные аргументы инструментов,
искажение фактов, отсутствие надёжного диалогового контекста и слабое
подтверждение обобщения за пределы небольших демонстрационных наборов.

## Файлы

- `build_neuroset.py` — архитектура, обучение, генерация и инструменты.
- `bench_suite.py` — сравнительные smoke tests и измерения скорости.
- `eval_det.py`, `eval_ood.py` — диагностические tool-тесты.
- `eval_utils.py` — выделение финального ответа и общие эвристики проверки.
- `tests/test_eval_utils.py` — регрессионные тесты оценивания без GPU.
- `bench_results.json` — архив исходных результатов с предупреждениями.
- `bench_corpus.txt`, `bench_corpus_en.txt` — тексты для языковой диагностики.

`runs/`, датасеты и локальная поисковая база — внешние/локальные артефакты,
а не файлы, поставляемые этим Git-репозиторием. Основной чекпойнт скачивается с HF.
Загрузчик предпочитает `final.pt`, затем `best.pt`, `last_model.pt`, `last.pt`;
при сравнении обязательно фиксируйте фактически выбранный файл.
